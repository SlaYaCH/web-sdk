Le Replay officiel Stake n’est pas une liste d’historique. Il reçoit directement dans l’URL un event précis avec replay=true, puis votre frontend appelle :

GET {rgs_url}/bet/replay/{game}/{version}/{mode}/{event}

et rejoue ce round-là. C’est exactement ce que demande la doc actuelle Stake.

Le SDK officiel fait d’ailleurs la même chose : quand replay=true, il ne fait pas d’authentification normale ; il récupère game, mode, version, event depuis l’URL et appelle requestReplay().

Donc pour votre jeu, je ferais deux systèmes distincts :

Previous Rounds / History dans le jeu
Là, on peut simplement conserver les rounds de la session actuelle que le jeu connaît déjà :

betID
mise
mode
payout
multiplicateur
état complet round.state
éventuellement heure locale

Et quand on clique sur Replay dans cette liste, on rejoue le round déjà stocké en mémoire, sans appeler /wallet/play et sans prétendre que betID est un Event ID.

Replay officiel Stake
Celui-là ne dépend absolument pas de votre liste locale. Stake ouvre le jeu avec par exemple :
?replay=true
&game=...
&version=28
&mode=normal
&event=12345
&rgs_url=...

Votre jeu prend event=12345, appelle /bet/replay/.../12345, reçoit le round et affiche l’animation. Aucun sessionID n’est requis en replay.

Et surtout : on ne doit pas essayer de fabriquer l’Event ID depuis betID ou depuis /bet/event. Le event du Replay est l’ID de simulation math. Stake explique que les résultats sont pré-calculés et mappés à un numéro de simulation dans les fichiers math.

Pourquoi vous galérez actuellement

Dans Neon Duck Race, votre /wallet/play renvoyait quelque chose comme :

{
  "round": {
    "betID": 1228998196,
    "amount": 1000000,
    "payout": 0,
    "payoutMultiplier": 0,
    "mode": "normal",
    "state": [...]
  }
}

Il n’y avait pas le véritable ID de simulation Replay dans cette réponse. Et /bet/event vous répondait seulement :

{"event":"0"}

Donc on ne peut pas déduire proprement l’Event ID officiel de ces deux réponses.

Ce n’est pas forcément un problème : Stake peut parfaitement connaître lui-même l’Event ID dans son historique côté casino et ouvrir votre frontend avec le bon event. C’est précisément pour cela que leur documentation parle d’une URL de replay partageable et d’un event fourni en entrée.

Ce qu’il faut absolument faire pour être conforme

En mode replay=true :

PAS de /wallet/authenticate
PAS de /wallet/play
PAS de /wallet/end-round

On fait uniquement :

GET /bet/replay/{game}/{version}/{mode}/{event}

Puis :

afficher un bouton Play ;
jouer toute l’animation ;
afficher mise, payout et résultat ;
proposer Play Again ;
empêcher toute vraie mise depuis le replay ;
gérer une erreur si l’Event ID n’existe pas.

Stake dit aussi explicitement qu’en review ils peuvent vous demander plusieurs Event IDs pour tester :

perte ;
victoire normale ;
big win ;
max win ;
bonus si le jeu en possède.

C’est là que se trouve le seul point restant à résoudre : comment trouver facilement ces Event IDs dans vos fichiers math.

Et ça, je peux vous le faire proprement. Si vous me donnez pour la slot — ou pour Neon Duck Race — le dossier math contenant :

index.json
books_....jsonl.zst
lookUpTable_....csv

je peux chercher dedans les numéros de simulation correspondants à une perte, une victoire, un gros gain, un max win, etc., et vous donner par exemple :

normal:
loss        -> event 12
small win   -> event 418
big win     -> event 7352
max win     -> event 18441

Ensuite vous les entrez directement dans l’outil Replay Stake et vous vérifiez que chaque Event ID rejoue exactement le bon résultat.

C’est beaucoup plus propre que d’essayer de récupérer l’Event ID depuis /wallet/play.
